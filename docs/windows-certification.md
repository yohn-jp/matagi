# Portable Windows candidate certification

The workflow runs on pushes to `main`, pull requests targeting `main`, and manual dispatch. It builds one Windows amd64 `matagi.exe`, records the exact source commit and SHA-256, and distributes that same artifact to the hosted Windows test shards. For pull requests, the source is `pull_request.head.sha`; every shard checks out that commit and verifies the downloaded candidate bytes before running. The aggregate rejects missing identity, failed jobs, missing shard evidence, and evidence for different bytes. Only a passing push to `main` can publish the certified candidate bytes and matching SHA-256 under `0.1.N-dev`.

The existing `startup`, `surface`, `transport`, `lifecycle`, and `single-instance` shards remain intact; the `updates` shard adds candidate replacement coverage. Together they cover candidate startup/shutdown, local API and desktop surfaces, bounded failure presentation, system OpenSSH configuration lookup, navigation policy, explicit English/Japanese selection and persistence over a candidate restart, localized Updates presentation, and a correlated start/restart/stop lifecycle through a deterministic SSH boundary. The lifecycle shard proves that an unowned Jinushi Run stays unknown, and that an absent correlated Run plus not-ready health evidence does not render `STARTING`. It also verifies non-empty, distinct submission IDs and the Matagi service correlation owner, loopback forwarding, and Matagi-owned tunnel cleanup.

The Updates candidate tests do not contact GitHub or download a release. One verifies the exact binary's localized Updates surface and explicit check control. The `updates` shard writes a local ready record around a copy of the sole candidate's bytes, first tampers with the stage and proves install is refused while the current executable keeps running, then restores those exact bytes and exercises the production replacement helper. It verifies that the old process exits, a new process starts from the same path, the previous executable remains at `.old`, and the helper records `applied`. The local ready record is only evidence for Windows file replacement and restart behavior; it does not claim an official release download. Updater release filtering, download, and checksum acceptance remain covered by deterministic package tests, and no test configures an alternate production release authority.

Hosted Windows evidence is **not** real-host certification. The deterministic SSH executable proves Matagi's Windows orchestration boundary only. It does not prove behavior against a real OpenSSH server, development host, Jinushi installation, Inari, or Yokodori. Issue #10 remains the sole authority for Windows → system OpenSSH → development host → Jinushi → registered-service real-host certification.

## Desktop ownership

The portable Windows matrix launches the certified executable twice under the same Windows user. The second launch must activate the existing native window and exit without composing a second Matagi runtime or tunnel authority. This is a Windows-side ownership check only; it does not certify a real remote Jinushi or development host.
