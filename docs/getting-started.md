# First Windows deployment

1. Install the Microsoft Edge WebView2 Runtime and Windows OpenSSH client. Configure your development host in your own `%USERPROFILE%\.ssh\config` (including any ProxyJump and IdentityFile) and confirm `ssh development true` succeeds without disabling host-key checks.
2. On the development host, install Jinushi and your service binaries by their supported procedures. Confirm the account can invoke `jinushi` and the service commands, and choose the actual working directories, readiness paths and **remote loopback** HTTP ports. Do not copy SSH credentials into Matagi.
3. Launch the production `matagi.exe`. Use **Connect a development environment** to enter an environment name and your existing SSH host alias. Matagi checks SSH and Jinushi before saving. Under Advanced, supply a bootstrap command only if the host needs an explicit command to start Jinushi; it is not an installer.
4. Use **Add service** in that environment. Enter a stable service name, the remote UI port, readiness path, working directory and start command with arguments. Command entry separates arguments at whitespace; use a host-side wrapper script when an argument requires quoting or embedded spaces. Registration saves the definition and does not start the remote process.
5. Inspect desired state, process, readiness and tunnel facts separately. A service without a correlated managed Run has process state unknown; an unready HTTP endpoint does not mean a launch is in progress. Use **Check Jinushi** to explicitly request supervisor bootstrap if needed, then **Start**, **Restart** or **Stop** for registered services. **Open** ensures the selected tunnel before navigating to the admitted Windows loopback address. Matagi never asks you to allocate a local port.

Select **English** or **日本語** in the language selector. The explicit selection is stored under Matagi's user configuration directory and wins across restarts; otherwise Matagi resolves the host language and falls back to English. Service names, SSH aliases, commands, paths and remote evidence remain literal.

Open **Updates** to select a channel and explicitly **Check for updates**. Only official Matagi GitHub releases are offered. **Download** stages and verifies the selected Windows executable against its release checksum. **Restart & update** re-verifies it, closes Matagi, replaces the executable through a helper and restarts the same path. The previous executable is retained beside it as `.old`. Viewing the page or choosing a channel does not check, download or install anything.

If the SSH connection fails, fix the user-managed SSH config/known_hosts instead of weakening host-key verification. If Jinushi is unavailable, check the configured supervisor-start command and its status on the host. For an unhealthy service, check its process and health path separately from tunnel availability. A manually started service without Matagi's correlation owner is not adopted as a managed Run.
