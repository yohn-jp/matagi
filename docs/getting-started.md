# First Windows deployment

1. Install the Microsoft Edge WebView2 Runtime and Windows OpenSSH client. Configure your development host in your own `%USERPROFILE%\.ssh\config` (including any ProxyJump and IdentityFile) and confirm `ssh development true` succeeds without disabling host-key checks.
2. On the development host, install Jinushi and the Inari/Yokodori binaries by their supported procedures. Confirm the account can invoke `jinushi` and the service commands, and choose the actual working directories, readiness paths and **remote loopback** HTTP ports. Do not copy SSH credentials into Matagi.
3. Copy `examples/first-deployment.json` into a private working document. Replace the illustrative `/path/to/...` directories, binary argv, ports and health paths with those of your installed services. Set `sshHost` to your existing SSH alias. `supervisorStartCommand` is run only when Jinushi is unavailable; set it to the supervisor-start argv supported by your host. It is not an installer. The example's `systemctl` command is illustrative, not a product default.
4. Launch the production `matagi.exe`. In the empty-state Add development environment form, paste the edited JSON and submit. Invalid documents are rejected before persistence. Matagi owns one local registry and one runtime; the environment appears immediately and is probed on the next poll. Restart Matagi to verify persistence.
5. Inspect connectivity independently of each service's process, readiness and tunnel states. Use Check / start Jinushi to explicitly request supervisor bootstrap if observation says unavailable, then use Start/Restart/Stop for registered services. Open ensures the selected tunnel before navigating to the admitted Windows loopback address. Matagi never asks you to allocate a local port.

If you first register only the environment using the on-screen starter JSON, use Register services on its empty service list to submit the complete document with the same environment and actual Inari/Yokodori definitions. Once services exist, registration cannot overwrite active configuration or tunnels. If the SSH connection fails, fix the user-managed SSH config/known_hosts instead of weakening host-key verification. If Jinushi is unavailable, check the configured supervisor-start command and its status on the host. For an unhealthy service, check its process and health path separately from tunnel availability.
